# Feedback to Rules

An editor's or owner's feedback on a draft is the main source of new writing rules. Each piece of feedback is generalized into a rule at the narrowest scope where it holds, so the same mistake does not recur in a later text. The six steps below turn a remark on one passage into a rule that a writer can apply to the next. They complement the derivation pipeline of this profile: there the source is material to derive context from; here it is a correction.

## 1. Generalize, then persist

Feedback on one passage names a failure in that passage. The rule states what the failure was an instance of, as a test with its exception, and is written into the scope where it holds: the base writing doctrine (a writing module's core profile) for what holds in every language and genre, a language module or profile for language mechanics, a genre profile for what changes per kind of text. Personal style, as distinct from a general ideal, goes into the owner's private module, never into a shared one.

## 2. Connect, do not duplicate

Before writing a new rule, find the existing principle it refines, extends, or conflicts with. Amend that principle, link to it, or record the conflict explicitly; a second rule that restates the first in other words is a defect in the rule set, as it would be in prose (the redundancy principle: every clause adds information). A conflict with an external or upstream guide goes to the record of house rulings that override other guides.

## 3. Never guess

When the generalization is uncertain — how broad it is, which scope it belongs in, or whether it is a preference or a principle — ask the owner, and offer two to four concrete alternatives, each phrased as the rule that would be written. An undecided question is recorded as a pending row in the rulings record and takes no position until the owner rules.

## 4. Test the candidate rule across cases

Before proposing a rule, test it against varied cases: the case that triggered it, a case in another language, a case in another genre and topic, and the edge cases where it would over-reach (headings, quotations, other authors' voices, standalone data such as tables and form fields). Report where it holds and where it does not; the places where it does not usually become its exception.

## 5. Infer the unstated cause

Feedback often marks what fails without saying why. Infer the most likely cause from the passage and the existing principles, state the inference, and confirm it with the owner before persisting a rule built on it. Where two causes are plausible, offer both.

## 6. Record provenance

Each persisted rule names the date and the decision it came from, in one line beside the rule or in the rulings record, so it can be revisited when a later decision narrows it. The rule itself is stated as a clean principle; the narrative of the round that produced it stays in the work record. Provenance that names people or private documents stays in a private module; a shared module carries only the clean principle.

Feedback, drafts and these internal process notes are working material: they are not published, quoted, or paraphrased in public text.
